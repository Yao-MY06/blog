- 人类用 obsidian 查看，也可手写更改
- 配合 unityMCP，AI基本可以90%完成

## 为什么觉得有用
系统化地把"模糊想法"变成"可执行计划"，且AI参与度高

# 方法论：Grill-Me 游戏策划工作流

## 适用条件
- 有一个模糊的游戏想法，需要细化成可执行的设计文档
- 需要 AI 不仅执行，还要"挑战"你的设计漏洞
- 使用 Unity/UE5 的 MCP 工具链（或计划使用）

## 模型选择
- **主模型：GPT-5.4**
  - 原因：长上下文 + 代码生成 + 游戏理解综合能力最强
- **备选：Claude-4**
  - 原因：逻辑分析更强，适合复杂系统拆解
  - 切换时机：当需要深度架构分析而非快速实现时

## 具体操作步骤

### Phase 0：策划草案
1. 用语音或文字输入"不长不短"的策划草案
   - 技巧：不要太长（AI会遗漏），不要太短（AI会脑补过多）
   - 建议：3-5个核心机制 + 目标平台 + 美术风格

### Phase 1：Grill-Me（挑战轮）
1. 提示词模板：
   ```
   我是一个游戏开发者，正在策划一款[类型]游戏。
   以下是我的策划草案：
   [粘贴草案]

   请你以资深游戏设计师的身份"grill me"——
   找出设计中的漏洞、矛盾、遗漏和不清晰之处。
   不要直接给答案，用提问的方式让我思考。
   每个问题都要足够具体，能迫使我做出明确决策。
   ```
2. 逐条回答 AI 的问题，不要跳过
3. 重复此过程直到 AI 确认"设计已足够清晰"

### Phase 2：拆解 Implementation Plan
1. 提示词：
   ```
   基于我们完善后的设计，请将其拆解为 implementation plan。
   要求：
   - 按功能模块划分 phase
   - 每个 phase 不超过 AI 上下文限制（约2000-4000 token执行量）
   - 标明依赖关系（哪些 phase 必须先完成）
   - 每个 phase 包含：目标、关键类/蓝图、验收标准
   ```

### Phase 3：分 Phase 执行
1. 每个 phase 开**独立 session**
2. 执行前让 AI 先读取 wiki 中相关条目（见 Phase 5）
3. AI 生成代码/配置/资产清单
4. 如果有 MCP（如 UnityMCP/UE5MCP），AI 直接操作引擎

### Phase 4：验收
1. 每个 phase 执行完，**另开 session**
2. 提示词：
   ```
   请验收 implementation plan 中 Phase X 的完成情况。
   原始验收标准：[粘贴]
   实际实现：[粘贴代码/截图描述]
   是否通过？如未通过，列出具体问题和修复方案。
   ```

### Phase 5：最终人测
1. 所有 phase 跑完后，人工运行测试
2. 记录 bug 和体验问题
3. 集中修复（可以再用一轮 AI）

## 关键技巧

### Wiki 维护（这套流程的灵魂）
- **工具**：Obsidian（人类）+ 纯 Markdown（AI读取）
- **结构**：
  ```
  game-wiki/
  ├── design/              # 设计文档（已确认的最新版）
  ├── architecture/        # 架构决策
  ├── api/                 # 内部API约定
  ├── assets/              # 资产清单和规格
  └── changelog.md         # 每次验收后的变更记录
  ```
- **使用方式**：
  1. 分 phase 执行时，在 prompt 中指定：`请读取 wiki/design/combat-system.md`
  2. 节省上下文：AI 不需要记忆全部设计，按需加载
  3. 验收后更新对应条目，确保"唯一真相来源"

### MCP 配合
- UnityMCP / UE5MCP 让 AI 可以直接操作引擎
- AI 90% 完成想法，人只花时间在最终打磨
- **注意**：MCP 需要本地环境，配置好安全措施

### Session 管理
- 永远不要在一个 session 里做所有事
- 每个 phase 独立 session 防止上下文污染
- 验收 session 和执行 session 必须分开

## 验证记录
- [ ] 未验证——计划在 UE5 第13-14周（项目整合阶段）首次尝试

## 关联卡片

- UE5-MCP工具链（待创建）

### 3.3 同时创建的 SOP

文件名：`03-工作流SOP/游戏策划-grill-me流程.md`

```markdown
# SOP：游戏策划 AI 驱动开发（Grill-Me 法）

## 触发条件
- 开始一个新游戏项目或新功能模块
- 有一个"大概想法"需要变成"可执行计划"

## 工具准备
- [ ] GPT-5.4 API 或网页版
- [ ] MCP 工具已配置（UnityMCP/UE5MCP）
- [ ] Obsidian wiki 仓库已初始化
- [ ] 语音输入设备（可选，加速草案阶段）

## 执行清单

### Step 1：草案（10-20分钟）
- [ ] 语音/文字输出策划草案
- [ ] 检查：是否包含核心机制、目标平台、美术风格？

### Step 2：Grill-Me（20-40分钟）
- [ ] 发送 grill-me prompt
- [ ] 逐条回答所有问题
- [ ] 重复直到 AI 确认设计清晰
- [ ] 将完善后的设计写入 wiki/design/overview.md

### Step 3：拆解 Plan（10分钟）
- [ ] 让 AI 拆解 implementation plan
- [ ] 检查 phase 粒度是否合理（每个可在一个 session 完成）
- [ ] 将 plan 写入 wiki/architecture/impl-plan.md

### Step 4：执行（每个 phase 15-30分钟）
- [ ] 开新 session
- [ ] 让 AI 读取相关 wiki 条目
- [ ] AI 生成代码/蓝图
- [ ] 有 MCP 则 AI 直接写入引擎
- [ ] 记录实际执行与 plan 的偏差

### Step 5：验收（每个 phase 5-10分钟）
- [ ] 开新验收 session
- [ ] 对照 plan 中的验收标准
- [ ] 通过 → 更新 wiki + 标记完成
- [ ] 未通过 → 记录问题 → 修复 session → 重新验收

### Step 6：人测（全部完成后）
- [ ] 运行游戏/功能
- [ ] 记录 bug 和体验问题
- [ ] 集中修复

## 质量检查点
- [ ] 设计文档在 wiki 中且最新
- [ ] 每个 phase 有独立的验收记录
- [ ] 最终版本与 wiki 一致

## 常见失败模式
1. **草案太长** → AI 遗漏关键点 → 拆成多个子系统分别处理
2. **一个 session 做太多** → 上下文污染 → 严格执行"一 phase 一 session"
3. **wiki 不更新** → AI 读取过期设计 → 养成"验收即更新"习惯
4. **跳过 grill-me** → 设计漏洞在后期爆发 → 不要省这一步

## 时间估算
| 项目规模 | 总时间 |
|---------|--------|
| 单个功能模块 | 2-4 小时 |
| 小型游戏原型 | 1-2 天 |
| 中型项目 MVP | 1-2 周 |
```

## 四、与 UE5/全栈学习路线的联动

### 4.1 什么时候用这套方法论？

| 学习阶段 | 应用场景 | 具体操作 |
|---------|---------|---------|
| UE5 第13-14周 | 做迷你格斗原型时 | 用 grill-me 完善战斗系统设计，然后分 phase 实现 |
| 全栈 项目期 | 做 AI SaaS 工具时 | 用同样流程做产品功能拆解，只是换成前端/后端 phase |
| 找实习期 | 准备面试项目讲解 | 让 AI grill 你的项目介绍，找出讲不清的地方 |

### 4.2 渐进采用策略

你现在还在学习阶段，不需要完整跑这套流程。建议这样渐进：

```
第1-4周（学习期）：
  └─ 只用一个技巧：遇到不懂的概念，让 AI "grill me"提问
  
第5-8周（项目初期）：
  └─ 开始维护简单 wiki（一个 markdown 文件即可）
  └─ 记录 ALS 参数和 GAS 设计决策
  
第9-12周（项目中期）：
  └─ 首次尝试完整的 grill-me + plan 拆解
  └─ 用在一个小功能上（如"冲刺技能系统设计"）
  
第13-16周（项目后期）：
  └─ 完整跑通整套流程
  └─ 把迷你原型当成第一个正式测试场
```
