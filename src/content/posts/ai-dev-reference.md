# AI 项目开发参考手册

本手册是项目SOP的按需参考页，只服务于两周项目中的具体决策、实施与复盘，不是日常入口。先由项目 SOP 确定当前需要哪一节，再复制对应模板；不要求每个项目填完全部内容。

## 证据规则

没有实测数据时必须准确区分：**未知**表示当前无法下结论，需同时记录待验证问题和验证方法；**不适用**表示该项与当前场景无关，需记录理由。不得用“不适用”回避尚未验证的事项。不得编造覆盖率、性能、成本节省、完成率、Star、用户反馈或面试反馈，也不得把主观判断包装成测量结果。

## 一页 PRD

适用：需要在开工前冻结问题、优先级和验收边界时。

```markdown
# [项目名] 一页 PRD

## 问题
- 当前发生了什么：[可观察事实]
- 为什么值得解决：[影响；无实测数据则写“未知”及验证方法]

## 用户
- 核心用户：[具体角色]
- 使用场景：[何时、为何使用]

## 范围
### Must
- [两周内必须完成且可验证的能力]
### Should
- [有价值，但不阻塞最小验证]
### Could
- [有余量再做]

## 本轮承诺范围
- [本次两周内承诺交付的 Must 项]

## 本轮不在范围
- [未承诺的 Must、Should、Could 或其他事项]

Should/Could 默认不进入当前两周承诺；只有正式调整范围并同步更新本 PRD、验收和排期后，才能移入“本轮承诺范围”。

## 约束
- 时间：[起止日期或“两周”]
- 技术/数据/权限：[已知限制]
- 风险：[未知则写待确认问题与验证方法]

## 验收
- [ ] 给定 [输入/前置条件]，系统应 [可观察行为]
- [ ] 错误路径 [场景] 能 [可观察处理]
- [ ] 证据保存在 [测试、日志、截图或演示位置]
```

## ADR（架构决策记录）

适用：存在真实取舍，且未来可能需要解释“为什么这样做”时。一项决策一份记录。

```markdown
# ADR-[编号]：[决策标题]

- 状态：提议 / 已接受 / 已替代
- 日期：[YYYY-MM-DD]
- 替代者：[无 / 替代本决策的 ADR 编号]
- 相关 ADR：[无 / ADR 编号与关系]

## 背景
[必须做决定的条件、目标与约束；未知项附待验证问题与验证方法]

## 决策
[选择什么，以及边界是什么]

## 备选
| 方案 | 优点 | 缺点 | 未选择原因 |
| --- | --- | --- | --- |
| [方案 A] | [ ] | [ ] | [ ] |
| [方案 B] | [ ] | [ ] | [ ] |

## 后果
- 正面：[ ]
- 负面/代价：[ ]
- 新风险：[ ]

## 复核触发
- 当 [成本、规模、依赖、质量或需求条件] 发生 [明确变化] 时重新评估。
```

## 单轮实施 Prompt

适用：把已拆分的一个步骤交给 AI 实施。一次只做一个可验证步骤；验证通过后，才开始下一轮。

```text
目标：
[本轮完成后唯一要出现的可观察结果]

上下文：
- 项目/模块：[ ]
- 相关文件或接口：[ ]
- 已知现状与证据：[ ]

约束：
- 必须遵循：[技术、风格、兼容性、安全要求]
- 不得假设：[未知信息]
- 不得编造任何测试、覆盖率、性能或用户结果。

本轮范围：
- [一个可验证步骤]

不在范围：
- [明确排除的重构、功能或文件]

验收：
- [ ] [给定条件] 时，[行为/输出]
- [ ] 运行 [具体检查] 并报告真实结果；无法运行则说明原因
- [ ] 不修改范围外内容

输出格式：
1. 修改摘要
2. 变更文件
3. 验证命令与真实结果
4. 未知点、风险与下一步（不得自动执行下一步）
```

## Review 记录

适用：评审一次实现、输出或实验，不把“看起来可以”当作结论。

```markdown
# Review：[对象 / 轮次]

- 观察行为：[实际输入、实际输出、复现条件]
- 评审结论：[接受 / 拒绝 / 需再测；评审对象；对应证据]
- 未知点：[未验证内容及验证方法；确无未知则写“不适用”并说明理由]
- 下一测试：[最小且能减少一个未知点的测试]
```

## Prompt 版本记录

适用：Prompt 规则变化可能影响行为，需要保留可比较证据时。

```markdown
| 版本 | 基准版本 | 改变规则 | 测试用例 | 评判标准/通过条件 | 观察结果 | 决定 |
| --- | --- | --- | --- | --- | --- | --- |
| v0.1 | 无（初始基准） | [初始规则] | [固定输入] | [可观察的通过条件] | [真实输出摘要；未测写“未知”并附验证方法] | 保留 / 回退 / 再测 |
| v0.2 | v0.1 | [新增/删除/改写了什么] | [与基准相同的固定输入] | [与基准相同的通过条件] | [真实输出摘要] | 保留 / 回退 / 再测 |
```

比较版本时明确基准版本，并保持测试用例和评判标准不变；否则只能记录观察，不能声称性能提升。

## 可选工程与发布闸门

这些闸门按风险选用，不是每个两周项目都要全做。先写明实际失败模式或交付场景，再只选择与之对应的适用检查；某领域被触发不代表要执行该行列出的全部检查。未知项附验证方法，不适用项附理由。

| 风险领域 | 何时启用 | 按实际风险选择的检查 |
| --- | --- | --- |
| 测试与错误路径 | 核心流程、输入不可信或失败会破坏数据 | 对应主流程做可重复验证；仅在相关时检查错误输入、依赖失败、超时、数据一致性或恢复方式 |
| 性能基线 | 存在明确的响应时间、吞吐、资源或上下文风险 | 只测受约束指标；固定环境、样本与方法，记录基线和波动，不用单次结果外推 |
| 安全与密钥 | 使用外部服务、敏感数据、文件或权限 | 按暴露面检查密钥、最小权限、敏感信息、依赖或输入边界中的适用项 |
| 日志诊断 | 异步流程、外部依赖或目标失败难以复现 | 只记录定位该失败所需的任务标识、阶段、错误与必要上下文，并排除密钥和敏感正文 |
| 交付与解释 | 需要他人运行、评审、演示或面试讲解 | 按实际交付场景选择 README、运行步骤、架构解释或演示；失败场景仅在演示目标需要时覆盖 |
| 开源仓库治理 | 计划公开协作、源码分发或发布可复用版本 | 按协作与分发风险选择许可证、贡献方式、安全报告渠道、版本与发布记录中的适用项 |

### 可选开源发布清单

仅在公开协作或分发场景中，按真实风险选择适用项并写入已启用闸门记录；不是每个两周项目都必须完成全部项目。

- [ ] README：说明用途、边界与必要前置条件。
- [ ] 运行步骤：他人能从干净环境复现启动或核心流程。
- [ ] 架构解释：说明关键组件、数据流和重要取舍。
- [ ] 演示：按实际交付目标准备成功流程；需要时覆盖相关失败场景。
- [ ] LICENSE / 许可证选择：明确允许的使用、修改与分发方式；未确定前不暗示已授权。
- [ ] CONTRIBUTING 或贡献方式：说明提交问题、变更、评审与行为约定；不开放贡献时写明渠道或边界。
- [ ] SECURITY 安全报告渠道（适用时）：提供非公开漏洞报告方式、响应边界与支持范围。
- [ ] 版本号与 CHANGELOG / 变更记录：定义版本规则，记录面向使用者的实际变化。
- [ ] 发布标签：标签与版本号、发布内容和对应提交一致。

### 发布前最小记录

```markdown
## 闸门汇总
- 已启用闸门：[名称列表]
- 未启用闸门：[名称] — 不适用；理由：[与当前场景无关的原因]
- 未启用闸门：[名称] — 风险已接受；风险：[具体风险]；接受人：[姓名/角色]；复核日期：[YYYY-MM-DD]

> 未启用项只在以上汇总记录。只能标“不适用”或“风险已接受”，不得使用其他模糊状态。

## 已启用闸门记录（每个已启用闸门复制一组）
### [闸门名称]
- 实际失败模式/交付场景：[ ]
- 本次适用检查：[只列与上述场景直接对应的检查]
- 证据与结果：[链接和真实结果；未知则写待验证问题与验证方法]
- 结论：通过 / 不通过 / 需再测
```

## 候选项目（仅供选择）

以下项目只是候选，不会自动启动。只有在项目SOP中完成选择、定义两周范围并明确验收后，才进入项目流程。

### AI 任务调度器

- 用户问题：个人或小团队把自然语言任务拆成执行步骤时，优先级、依赖与完成定义不清，容易反复改计划。
- 最小两周验证：输入一组带截止时间与依赖的任务，生成可人工确认的排序和理由；用固定样例验证依赖不冲突，并记录人工修改点。
- 为何不自动启动：需要先确认真实任务样本、调度规则和错误代价；没有这些信息，容易做成无法验证的通用待办应用。

### 代码评审助手

- 用户问题：评审者需要从变更中快速发现与需求、正确性和风险相关的问题，同时保留可复现证据。
- 最小两周验证：针对一个限定技术栈和一组已知缺陷样例，输出带文件位置、严重级别、理由与验证建议的 Review 记录；统计只能基于真实样例运行结果。
- 为何不自动启动：必须先确定仓库权限、评审标准、数据安全边界和基准样例；否则无法判断建议是否有效。

### 知识库助手

- 用户问题：用户知道资料存在，却难以找到来源明确、可追溯且不过度推断的答案。
- 最小两周验证：基于一小组批准文档回答固定问题，每个结论附来源；对资料外问题明确回答“未知”，并记录检索失败案例。
- 为何不自动启动：需要先明确文档范围、更新频率、访问权限和引用标准；资料未治理时，助手会放大过期或冲突信息。

## 使用边界

- 按需打开：仅在项目 SOP 指向 PRD、ADR、Prompt、Review、版本记录或发布闸门时使用对应节。
- 两周约束：模板服务于缩小范围和获取真实证据，不用于堆积长期设想。
- 不是日常入口：日常推进回到当前状态面板或当前交付物；项目SOP仅在需要查阅流程规则时按需打开。本页不承担提醒、排期或自动开项。
- 所有数字与结论必须能追溯到真实测试或来源；无法下结论时写“未知”并记录验证方法，与场景无关时写“不适用”并记录理由，不得编造。
